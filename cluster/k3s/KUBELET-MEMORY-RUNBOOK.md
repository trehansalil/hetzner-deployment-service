# Kubelet memory safety runbook (node `portfolio`)

**Status:** not applied. Config file: [`kubelet-memory.yaml`](kubelet-memory.yaml).
**Scope:** single-node k3s v1.34.5+k3s1, Hetzner `portfolio` (hel1-dc2, 4 vCPU, 7.6 GiB RAM, 8 GiB swapfile, pods NoSwap).

## 1. Problem

Live kubelet config (`/var/lib/rancher/k3s/agent/etc/kubelet.conf.d/00-k3s-defaults.conf`, generated by k3s):

```yaml
evictionHard:
  imagefs.available: 5%
  nodefs.available: 5%
evictionMinimumReclaim:
  imagefs.available: 10%
  nodefs.available: 10%
```

- No `memory.available` threshold, so the kubelet never evicts for memory.
- No `systemReserved` / `kubeReserved`, so allocatable equals capacity (`7937228Ki`) and `kubepods.slice` `memory.max` equals the whole host (`8127721472`).
- k3s runs from a stock unit (`ExecStart=/usr/local/bin/k3s server`, empty `k3s.service.env`). `/etc/rancher/k3s/config.yaml` and `config.yaml.d/` do not exist.

As a result, memory exhaustion goes straight to the kernel OOM killer. It prefers pods (`oom_score_adj` 992–1000), which is how traefik and postgres were killed on 2026-09-17.

## 2. Measurements behind the numbers (2026-09-25)

The figures are PSS from `/proc/*/smaps_rollup`, grouped by cgroup, excluding `kubepods*`:

| Group | PSS | Swapped | Notes |
|---|---|---|---|
| `k3s.service` | **1042 MiB** | 83 MiB | `k3s server` 827 MiB (apiserver, controller, scheduler, kine/sqlite, kubelet, flannel in one process), containerd 104 MiB, shims |
| other `system.slice` | 109 MiB | 44 MiB | journald 51, multipathd, snapd, synchub, cron |
| `user.slice` | **1968 MiB** | **3664 MiB** | 2 interactive Claude sessions (~350 + ~300 MiB), happy (~200 + ~110 MiB), codebase-memory-mcp ×3, serena/LSPs, paseo, mcpvault |
| pods (`kubepods.slice`) | 2616 MiB current | 0 | `kubectl top node`: 5795 Mi used overall |

The cgroup view agrees: `k3s.service` memory.current is 1172 MiB (941 anon), `user.slice` has 1706 MiB anon plus 3772 MiB swap. n8n is a pod (`infra/n8n`, 215 Mi working set, 256Mi request), so it is already covered by pod accounting.

**Chosen values and why:**

- `kube-reserved=memory=1Gi`, **not 512Mi.** k3s alone measures about 1.0 GiB PSS. 512Mi would under-reserve by half and let pods crowd the control plane.
- `system-reserved=memory=1Gi`. Real system daemons use about 110 MiB. The rest is headroom for sshd, apt, journald bursts and a quiet interactive session.
- **The interactive user.slice is not covered.** It uses about 2 GiB resident plus 3.6 GiB swapped. Reserving for it honestly (about 3 GiB total system+kube) would drop allocatable to about 4.4 Gi. That trade is only sensible after Option A or B (see §4 and §6).
- `eviction-hard memory.available<300Mi`. The kubelet housekeeping loop is about 10s, so 300Mi is the floor at which it can still act before the kernel does.
- `eviction-soft memory.available<600Mi` with a 1m30s grace. This evicts the pod most over its request gracefully before the hard line is reached.

## 3. Effect on allocatable and on the RFC-050 branch

Capacity `7937228Ki` = 7751 Mi. Allocatable = capacity − system − kube − eviction-hard.

| Config | Allocatable | `kubepods.slice` memory.max |
|---|---|---|
| Today | **7751 Mi** | 7751 Mi (the whole host) |
| Requested (1Gi / 512Mi / 300Mi) | 5915 Mi (`6057164Ki`) | 6215 Mi |
| **Shipped (1Gi / 1Gi / 300Mi)** | **5403 Mi** (`5532876Ki`) | 5703 Mi |

Pod memory **requests** on the node today total **2904 Mi**. `pageindex-mcp-worker` is at 512Mi and docling-service is not deployed yet.

The `feature/pageindex-docling-service` branch changes this:

- docling-service: +2560Mi, Recreate strategy, 1 replica.
- worker: request 512Mi → 1Gi. Surge is not a concern because `maxSurge: 0`.

| Scenario | Requests | Today (7751) | Requested (5915) | Shipped (5403) |
|---|---|---|---|---|
| Current, no docling | 2904 Mi | fits | fits | fits |
| Branch, worker ×1 | **5976 Mi** | fits | **docling Pending** | **docling Pending** |
| Branch, worker ×2 (KEDA max; the ScaledObject is currently paused) | **7000 Mi** | fits (on paper) | Pending | Pending |
| Option A: docling on its own node, worker ×2 | 4440 Mi | fits | fits | fits |

Transient extras are on top of these: the `claude-mem-pg-sync` CronJob pod adds +64Mi, and `claude-mem-gen-worker` KEDA scaling to 5 adds up to +256Mi.

**Conclusion:** on the current 7.6 GiB node, no honest reservation leaves room for the docling-service branch. "Fits today" only holds because allocatable pretends k3s and the host use 0 bytes. That is the capacity problem behind the A-vs-B decision.

Recommended order: apply this config **together with or after** Option A or B. If you apply it first, docling-service will sit `Pending` (Insufficient memory). That is the safe failure mode, not an OOM.

## 4. Known limits (read before relying on this)

1. **Eviction only protects the host from pods, not from host processes.**
   - The kubelet's `memory.available` signal is host-wide (root cgroup working set).
   - If a Claude session or an unbounded `pytest` (the 2026-09-17 trigger) eats the RAM, the kubelet responds by **evicting pods**, starting with the pods most over their request. That beats a random kernel OOM of traefik, but it still costs pods.
   - The real fix for runaway host processes is capping them:
     - `make test` in pageindex already runs in its own scope with `MemoryMax`.
     - Optionally cap interactive sessions with a systemd drop-in, not shipped here and not applied, e.g. `/etc/systemd/system/user.slice.d/50-memory.conf` with `[Slice] MemoryHigh=2560M MemoryMax=3G`. Size it only after watching `systemctl status user.slice` for a week, because a cap that is too tight kills the agent sessions themselves.
2. **Fast spikes can still beat the kubelet.**
   - A process that allocates GiBs in a few seconds can reach the kernel OOM killer between two housekeeping passes.
   - The `kubepods.slice` `memory.max` (now capacity minus reservations) contains pod-side spikes inside the pods cgroup. Host-side spikes are only contained by per-process caps.
3. **Swap blurs the signal.** Host processes can swap (the swapfile is currently 4.1 of 8 GiB used), so the kernel pushes user.slice to swap before `memory.available` falls to 600/300 Mi. Pods are NoSwap. Swap is not in `/etc/fstab`, so it does not survive a reboot.
4. **Allocatable is scheduler accounting.** It prevents over-scheduling by requests, but it does not limit actual usage above requests. Pods with limit ≫ request (node limits total 11964Mi against 7751 capacity) still overcommit.

## 5. Apply

Prerequisites: shell on `portfolio` as root, plus a maintenance window. The expected API outage is about 30–90 s.

1. Pre-check: current requests must fit the new allocatable. A kubelet restart re-admits running pods, and pods that no longer fit can be rejected (`OutOfmemory`).
   ```bash
   kubectl describe node portfolio | sed -n '/Allocated resources/,/Events/p'
   # memory Requests must be < 5403Mi (shipped values) — today 2904Mi.
   ```
2. Save the current effective config for the rollback diff:
   ```bash
   kubectl get --raw /api/v1/nodes/portfolio/proxy/configz \
     | jq '.kubeletconfig | {evictionHard, evictionSoft, systemReserved, kubeReserved}' \
     > /root/kubelet-configz-before.json
   ```
3. Install the drop-in. An empty base `config.yaml` is created too, because k3s issue #9567 reports drop-ins being ignored when the base file is missing:
   ```bash
   install -d -m 0755 /etc/rancher/k3s/config.yaml.d
   [ -f /etc/rancher/k3s/config.yaml ] || install -m 0600 /dev/null /etc/rancher/k3s/config.yaml
   install -m 0600 cluster/k3s/kubelet-memory.yaml /etc/rancher/k3s/config.yaml.d/10-kubelet-memory.yaml
   ```
4. Restart k3s:
   ```bash
   systemctl restart k3s
   ```
   **What restarts:**
   - The unit uses `KillMode=process`, so only the `k3s` process restarts (apiserver, kubelet, kine and flannel are all inside it).
   - containerd-shims and **containers keep running**. Pods are not recreated as long as step 1 passed.
   - Ingress traffic keeps flowing through traefik. The Kubernetes API, `kubectl`, the CI deploy workflow and KEDA scaling are unavailable until k3s is `Ready`, typically 30–90 s on this sqlite/kine datastore.
5. Verify:
   ```bash
   systemctl is-active k3s && kubectl get node portfolio
   kubectl get --raw /api/v1/nodes/portfolio/proxy/configz \
     | jq '.kubeletconfig | {evictionHard, evictionSoft, evictionSoftGracePeriod, systemReserved, kubeReserved}'
   # expect evictionHard {memory.available:300Mi, nodefs.available:5%, imagefs.available:5%}
   kubectl get node portfolio -o jsonpath='{.status.allocatable.memory}{"\n"}'   # expect 5532876Ki
   cat /sys/fs/cgroup/kubepods.slice/memory.max                                   # expect 5980237824 (5703Mi)
   kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded
   ```
   If `evictionHard` came back **without** the `nodefs`/`imagefs` entries, roll back immediately. Disk-pressure eviction is then off.

## 6. Option-specific values

| Node | system-reserved | kube-reserved | eviction-hard memory | Notes |
|---|---|---|---|---|
| `portfolio` 8 GB (as shipped) | 1Gi | 1Gi | 300Mi | branch docling does not fit (§3) |
| `portfolio` after Option B (16 GB) | 2Gi | 1Gi | 500Mi | 2Gi actually covers the measured user.slice; re-measure first |
| Option A docling agent (cx23, 4 GB) | 256Mi | 256Mi | 200Mi | agent-only k3s (no apiserver) is much smaller; set via the cloud-init in `option-a-docling-node/` |

## 7. Rollback

```bash
rm /etc/rancher/k3s/config.yaml.d/10-kubelet-memory.yaml
# remove config.yaml only if step 3 created it empty:
[ -s /etc/rancher/k3s/config.yaml ] || rm /etc/rancher/k3s/config.yaml
systemctl restart k3s
kubectl get node portfolio -o jsonpath='{.status.allocatable.memory}{"\n"}'   # back to 7937228Ki
```

The rollback has the same impact as applying: a 30–90 s API outage, with containers kept running.
